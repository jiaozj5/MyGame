# 事件数据契约 v0.1

## 1. 本文对应的实现

本文解释当前 `prototype/engine.py` 实际消费的 JSON 数据及执行边界，对应：

- `examples/world.json`：这一局的初始世界实例。
- `content/events.json`：可执行事件模板目录。
- `content/personality-dimensions.json`：行为观察的设计说明与适配说明；引擎当前没有加载它来自动计算人格分数。

这是 **Python 领域校验器加 JSON 样例**。目前没有完整的 JSON Schema 结构验证，没有生成资产管理平台，也没有“任意 AI 内容导入后即可安全运行”的能力。以下字段表描述的是当前支持的约定，不表示校验器已能对所有缺字段、错类型、未知字段给出统一错误。

运行内容只有三个事件：

| 模板 ID | 触发方式 | 当前功能 |
|---|---|---|
| `friend.loan_request` | `ambient` | 朋友请求借款，选择全额、部分、付出精力尝试其他办法或拒绝 |
| `friend.loan_due` | `scheduled` | 已存在借款到期，接受全额还款、延长日期或保留债权并结束本次催促 |
| `friend.old_letter` | `ambient` | 朋友死亡后处理一封事先已经存在的信 |

`docs/event-library-v0.1.md` 中的十二个人生事件是内容设计样本，尚未全部转换成这个契约下的可执行资产。

## 2. 世界实例与事件模板必须分开

世界实例回答“这一局现在是什么情况”；事件模板回答“满足条件时，哪些行动可以怎样改变它”。

例如，模板写 `friend.cash`，通过角色绑定访问本次朋友的资金。世界实例写 `persons.f.cash = 50`。借款成立后变更的是这一局的世界实例，模板中的金额、条件和文案保持原样。

当前借款模板虽然使用 `friend` 角色，仍通过 `facts.friend_request_person` 限定实际提出请求的人；信件模板也直接引用 `artifacts.letter_f`。这两个入口是有意保留的演示约束，还不是适用于任意请求者和任意遗物的通用模板系统。

### 2.1 顶层版本字段

| 字段 | 世界实例 | 模板目录 | 当前含义 |
|---|---|---|---|
| `schema_version` | 有 | 有 | 必须等于引擎支持的 `0.1.0` |
| `ruleset_id` | 有 | 有 | 必须等于 `smalltown-v0.1` |
| `setting_id` | 有 | 每个事件上有 | 运行时事件必须与当前世界场景匹配；样例为 `smalltown` |
| `revision` | 有 | 无 | 世界每次成功提交后递增，用于拒绝过期菜单 |
| `events` | 无 | 有 | 事件模板数组，事件 ID 在目录中唯一 |

这些版本字段目前用于拒绝不兼容输入，不代表已经有旧存档迁移、内容版本并存或线上发布系统。

### 2.2 世界实例字段

| 字段 | 结构与用途 | 当前检查或限制 |
|---|---|---|
| `day` | 从 0 开始的整数世界日 | 非负；推进操作只接受正整数天 |
| `player_id` | 玩家人物 ID，例如 `p` | 必须存在于 `persons` |
| `persons` | 人物 ID 到人物记录的字典 | 字典键必须与人物的 `id` 一致 |
| `relationships` | 有方向的关系数组 | 人物存在；同方向同类型不能重复；需要反向关系，数值可以不同 |
| `facts` | 可变状态标记字典 | 用于请求是否开启、信件是否处理等；只由允许的操作写入 |
| `historical_facts` | 历史事实 ID 到事实记录的字典 | 检查时间和参与者；普通事件效果不能改写此表 |
| `artifacts` | 物件 ID 到物件记录的字典 | 检查作者、创建时间和显式声明的事实引用 |
| `loans` | 借款 ID 到借款记录的字典 | 检查人物、金额、日期和状态 |
| `tasks` | 未来借款到期任务数组 | 当前任务结构专用于借款；不是通用 NPC 日程 |

**人物记录的当前字段：**

- `id`、`name`、`birth_day`、`alive`、`death_day`、`location`。
- `cash`、`housing_reserve`：非负整数。
- `energy`、`health`、`stress`：0—100 整数，越界时报错，不自动截断。
- `knowledge`：`事实 ID → 获知日`。事实必须存在，获知时间不能早于事实发生和本人出生，也不能晚于本人死亡。
- `repayment_willing`：样例朋友使用的布尔意愿字段。还款操作要求其值严格为 `true`；它不是完整的 NPC 决策模型。

当前支持的关系类型为 `friend`、`parent`、`child`，反向分别为 `friend`、`child`、`parent`。每条关系保存 `from`、`to`、`kind`、`trust`、`closeness`，后两项范围均为 0—100。要求存在反向记录不意味着信任必须对称。

### 2.3 样例资源的准确含义

初始玩家为 24 岁：`day = 0`，`birth_day = -8760`，年龄按整除 365 天计算。玩家现金为 600，`housing_reserve = 500` 是希望留下的住房预算目标。

- 借出 400 后，现金为 200，低于住房预算目标，但满足支付条件，因此原型允许选择。
- 借出 100 后，现金为 500；这只说明没有低于该目标，不代表生活风险已经完全消失。
- 500 不是冻结金额，也不是当前已实现的房租到期账单。
- 原型没有工资、房租、食物或精力恢复的日常结算。调用时间推进不会自动收取费用。
- “一起寻找其他办法”当前只消耗 10 点精力并记录尝试标记，没有推进小时或天，也不保证找到替代资金。

完整游戏若要表现交租压力，需要新增明确的到期义务和费用结算规则。所有演示数值都是待平衡假设。

## 3. 事件模板字段

| 字段 | 当前支持的含义 |
|---|---|
| `id` | 稳定事件 ID；同目录内唯一 |
| `version` | 正整数版本；已发出的事件菜单会绑定此版本 |
| `title` | 界面标题；不会产生世界事实 |
| `setting_id` | 必须匹配世界的 `setting_id` |
| `trigger` | 仅支持 `ambient` 或 `scheduled` |
| `age_range` | `[最小年龄, 最大年龄]`，两端包含在内；当前只检查顺序并在运行时比较 |
| `actors` | 除玩家以外的角色选择条件，见下一节 |
| `preconditions` | 整个事件的前提列表，全部必须成立 |
| `description` | 文本及 `{friend.name}`、`{player.cash}` 等路径占位符 |
| `context_tags` | 记录到选择证据中的情境标签；当前不用于叙事调度 |
| `choices` | 选项数组；至少两个作者写好的选项，ID 在事件内唯一 |

`ambient` 意味着可按当前事实筛选，不意味着会自动随机发生。`scheduled` 必须绑定一个待处理且已到期的任务。引擎目前只做合法性筛选，没有紧迫性评分、戏剧节奏、随机抽取、长期内容覆盖或大模型调度。

`description` 通过路径读取状态并替换文本，不运行表达式和代码。文案不会自动创建它声称的事实；但当前也没有语义检查器证明每一句自由文本都与状态一致。

### 3.1 角色选择与实际绑定

模板中的选择条件示例：

```json
{
  "actors": {
    "friend": {
      "relation": "friend",
      "alive": true,
      "same_location": true
    }
  }
}
```

实际发生时的绑定为：

```json
{"player": "p", "friend": "f"}
```

当前规则：

1. `player` 必须绑定 `world.player_id`，且玩家必须健在。
2. 绑定键必须恰好是 `player` 加模板声明的角色；同一个人物不能占用两个角色。
3. 每个人物 ID 必须存在；NPC 必须符合玩家指向他的关系类型。
4. `alive: true` 要求健在，`alive: false` 要求已经死亡。后者用于遗物、回忆等内容，不等于允许死者执行转账。
5. `same_location: true` 要求双方地点相同；`false` 表示不检查同地条件，并非要求两地分离。
6. 自动候选搜索目前只支持一个 `friend` 角色；它枚举已有 NPC 并筛选。尚未实现任意多个角色的自动分配。

任务事件不重新随机寻找朋友，而是沿用任务中保存的绑定，并检查与对应借款的债权人、债务人一致。因此，原朋友去世后，系统不能找另一个朋友替他还钱。

## 4. 条件格式与硬门槛理由

`preconditions` 和选项中的 `requirements` 使用相同条件格式：

```json
{"path": "player.cash", "op": "gte", "value": 100}
```

动态比较值只支持单一 `ref` 路径：

```json
{"path": "friend.cash", "op": "gte", "value": {"ref": "loan.amount"}}
```

| 字段 | 含义 |
|---|---|
| `path` | 从运行上下文读取的点分隔路径，如 `facts.letter_handled` |
| `op` | 仅支持 `eq`、`gte`、`lte` |
| `value` | 直接值，或恰好只有 `ref` 键的动态路径对象 |

运行上下文包含世界顶层字段、已绑定角色，以及任务事件中的 `loan`。所有条件按“并且”解释；没有表达式求值、任意函数、`or`、正则条件或自定义脚本。

`eq` 要求双方类型和值都相同；`gte`、`lte` 要求双方是整数，布尔值不当成整数使用。路径缺失会产生明确的规则错误，不悄悄视为 0 或 `false`。

### 4.1 前提与选项限制的区别

- 事件前提不满足：本次事件不进入合法候选。
- 事件成立、某选项不满足：菜单保留选项，返回 `available: false` 与 `locked_reason`。
- 除显式 `requirements` 外，效果试算失败也会锁定选项，例如余额不足、人物已死亡、数值越界、债务上下文不匹配。

菜单返回的单项字段为 `id`、`label`、`available`、`locked_reason`。当前理由是面向规则验证的原始错误信息，例如 `player.cash gte 100（当前：50）`；还没有统一的玩家文案映射。

住房储备目标不是硬门槛；“善良”“勇敢”等人格判断也不参与当前选项锁定。技术性内容错误若导致选项锁定，应修正文案或规则，不能包装成角色的心理限制。

## 5. 选项、效果与七种操作

### 5.1 选项字段

| 字段 | 当前用途 |
|---|---|
| `id` | 本事件内唯一的选项 ID |
| `label` | 玩家看到的选项文字 |
| `requirements` | 选择前必须满足的条件；空数组表示无额外显式条件 |
| `effects` | 按顺序试算的操作数组；可以为空 |
| `evidence` | 作者预先标注的行为观察数组；可以为空 |

空 `requirements` 不保证选项可执行，仍须通过全部效果与世界规则检查。空 `effects` 也可以记录一次选择，并结束当次到期任务；它不一定意味着“什么都没发生”。

当前目录中的部分借款选项片段：

```json
{
  "id": "lend_partial",
  "label": "借出100元，并说明自己的预算",
  "requirements": [
    {"path": "player.cash", "op": "gte", "value": 100}
  ],
  "effects": [
    {"op": "transfer", "from": "player", "to": "friend", "amount": 100},
    {"op": "create_loan", "creditor": "player", "debtor": "friend", "amount": 100, "due_in_days": 30},
    {"op": "set_fact", "key": "friend_request_open", "value": false}
  ],
  "evidence": [
    {"dimension_id": "care", "behavior": "partial_material_support", "strength": "limited"},
    {"dimension_id": "risk_taking", "behavior": "limit_financial_exposure", "strength": "limited"}
  ]
}
```

### 5.2 操作白名单

目前只允许以下 **七种** `op`。白名单之外的效果不能靠 JSON 文本添加能力，必须修改引擎并验证新规则。

| `op` | 操作参数 | 当前语义与边界 |
|---|---|---|
| `transfer` | `from`、`to`、`amount` | 角色之间转移正整数现金；金额可用 `ref` 读取。双方必须健在且不同，付款方余额足够 |
| `adjust` | `actor`、`field`、`delta` | 只调整 `energy`、`health`、`stress`，增量为整数；每一步都不得越过 0—100 |
| `set_fact` | `key`、`value` | 只写 `world.facts`；值限布尔、字符串、整数，不支持嵌套对象、浮点或通过 `ref` 赋值 |
| `adjust_relation` | `from`、`to`、`field`、`delta` | 只调整已经存在的单向 `friend` 关系的 `trust` 或 `closeness`；双方健在，结果在 0—100 内 |
| `create_loan` | `creditor`、`debtor`、`amount`、`due_in_days` | 金额与延迟都是正整数；创建借款和绑定的 `friend.loan_due` 任务，必须有本次选项内此前完成的对应转账 |
| `settle_loan` | 无额外参数 | 仅在借款任务上下文中，全额从朋友转回玩家；要求对方健在、愿意还款且钱足够，之后借款状态为 `repaid` |
| `reschedule_loan` | `days` | 仅在借款任务上下文中，正整数天；将同一借款与任务的到期日一起改为“当前日 + days” |

补充限制：

- `create_loan` 自己不转账；引擎要求同一选项内有此前发生、方向和金额相同的 `transfer`。一次转账不能被重复用于创建多笔相同债务。
- `settle_loan` 目前只支持整笔还款，没有分期、部分还款、利息或债务转让。
- `reschedule_loan` 目前只是延期操作，没有完整的双方谈判过程。
- `adjust_relation` 的结果由审核过的模板直接指定。例如全额借款后朋友对玩家的信任增加 4，这是待平衡的作者假设，不是模型推演出的心理事实。
- `set_fact` 当前没有为每个可变事实设置专门的键白名单；因此资产仍须由可信作者审核。它无法直接写 `persons`、`historical_facts` 或其他顶层表。
- 死亡和推进时间通过引擎的独立入口执行，不是上述事件效果之一。当前资产不能写一个 `kill` 或 `advance_time` 就获得该能力。

## 6. 一次选择怎样提交

事件菜单对应一个 `Offer`，包含 `event_id`、`event_version`、世界 `revision`、实际 `bindings`，以及可选的 `task_id`。

执行原则是**在副本中试算，通过后整体提交**：

1. 检查菜单的世界版本是否仍然有效，以及事件版本、人物、地点、年龄和前提是否仍成立。
2. 对选项检查硬门槛，在世界副本中按顺序执行效果。
3. 检查转账与建债配对、操作权限、资源范围、人物状态和世界关联规则。
4. 失败则保留原世界，不产生一半转账、一半建债的状态。
5. 成功后递增 `revision`，保存状态快照与本次选择记录，再接受下一次操作。

查询可用选项也要试算，不能只看 `requirements`。玩家真正提交时再次计算，避免沿用过时结果。过期菜单必须重新取得，不能直接把其中选项套用到新世界。

这是本地、单引擎实例中的受控提交机制，不代表已实现数据库事务、多个玩家并发、分布式锁或远程幂等接口。调用者也不应直接修改引擎的状态对象来绕过入口。

### 6.1 选择记录与回放

成功选择的记录包含：事件与版本、选项 ID 和文字、角色绑定、任务 ID、全部菜单项及锁定原因、年龄、情境标签、选择前资源、玩家知识、实际展示的文本、现金负担及作者观察标签。

`cash_cost` 汇总本次试算实际产生的转账中、以玩家为付款人的现金转出，包含动态解析金额；它统计转出总额，不是净资产变化，也不是涵盖精力、时间和机会成本的总成本计算器。`cash_cost_share` 为该金额占选择前现金的比例，选择前现金为 0 时为 `null`。`below_housing_reserve_after` 只比较结果现金与住房目标。

提交记录保留前后状态摘要、提交后快照，以及连接前一条记录的 `previous_entry_hash` 和覆盖本条记录内容的 `entry_hash`。回放检查记录链、内容摘要、状态摘要和序号，再按已有快照恢复状态；不重新调用模型、不重新抽取内容，也不以新版模板重演旧人生。摘要检查不等于带可信签名的防篡改存证；当前没有线上审计或版本迁移服务。

## 7. 后续任务：到期重验与取消

### 7.1 借款与任务记录

借款字段：

```text
id, creditor, debtor, amount, created_day, due_day, status
```

借款状态仅为 `outstanding`、`repaid`、`deceased_pending`。`amount` 保留整笔借款金额，当前没有独立的分期支付明细或可逐次减少的剩余本金字段。

任务字段：

```text
id, event_id, loan_id, due_day, bindings,
requires_alive, status, cancellation_reason
```

任务状态仅为 `pending`、`resolved`、`cancelled`。待执行任务必须对应一笔未结借款，任务到期日与借款到期日一致；绑定为债权人 `player` 和债务人 `friend`。当前创建逻辑固定指向 `friend.loan_due`，尚未抽象为任意任务生成器。

### 7.2 时间推进的行为

- 推进必须停在途中最早的待执行任务到期日，不能跳过还款日。
- 时间推进前后都检查已到期任务：对应事件必须仍成立，且至少一个选项能在当前状态副本上完整试算通过；不把最初的计划当成未来已经发生的事实。
- 已到期但可处理的任务需要先解决，再继续推进日期。
- 前提失效或没有可执行选项的到期计划进入取消状态，保留取消原因；不会自动给玩家补造一个结果。
- 延期同时更新任务和借款日期，任务继续等待；接受还款或保留债权并结束催促会结束本次任务。
- 结束催促只结束任务，未还债权仍然存在；当前不会自动再次安排催收事件。

到期检查只覆盖当前已实现的条件与任务类型。未来一般 NPC 计划的优先级、旅行耗时、不可联系状态、重新协商和自动替代方案尚未实现。

### 7.3 死亡与遗留内容

独立的 `mark_dead` 操作要求人物存在、仍健在并提供非空原因；提交后记录死亡日，将健康置为 0，取消所有要求该人物健在的待执行任务。涉及他的未结借款改为 `deceased_pending`，历史债权不会被删除或自动视为已清偿。

死亡后的主动效果仍然受限制：`transfer`、`adjust` 和关系调整所涉及的行动人物必须健在。`friend.old_letter` 可以绑定死者，是因为它只读取身份与既存遗物，并更新玩家是否处理信件的事实标记。

信件样例在初始世界就有作者、创建日、事实引用及文本。校验器检查信的创建时间不晚于作者死亡，显式引用的事实在写信时已被作者知道。**校验器没有理解自然语言正文**；如果正文暗示未列入 `fact_ids` 的未来知识，当前检查不会自动发现。叙事审核仍然必要。

当前没有继承、遗产抵债、健康致死或自然老化模拟。健康变为 0 不会隐式调用死亡入口。

## 8. 行为证据字段

每条 `evidence` 的结构为：

```json
{
  "dimension_id": "care",
  "behavior": "partial_material_support",
  "strength": "limited"
}
```

| 字段 | 实际约定 |
|---|---|
| `dimension_id` | 必须是引擎已列出的观察方向 ID |
| `behavior` | 作者写的行为标签；当前没有完整的行为词表结构校验 |
| `strength` | 只接受 `limited` 或 `ambiguous`，都是作者标注，不是统计置信度 |

当前八个方向 ID 为：`exploration`、`persistence`、`social_initiative`、`care`、`fairness`、`conflict_style`、`risk_taking`、`help_seeking`。本轮三个事件只提供其中少数方向的观察。

引擎将“实际可执行选项至少两个”记录为 `opportunity`，只有通过这一机械门槛的选择才进入 `observations()` 输出。它不能证明这些选项对某个维度都有意义，也不能证明玩家拥有充分信息或不受其他压力影响。

`observations()` 输出原始标签及 `evidence_id`、事件 ID、情境、选择前资源、现金成本和锁定选项。完整菜单和其他上下文仍在原选择记录中。当前没有人格分数、MBTI 类型、心理诊断、置信概率或从角色推断真实玩家人格的算法。

内容设计建议每个事件最多观察两个方向，但当前目录校验器没有强制这个数量上限。延期标签 `negotiated_extension` 也只是现有标签，不能据此宣称引擎已经模拟双向协商。更严格的解释边界见 `docs/personality-v0.1.md`。

## 9. 审核覆盖与未来扩展

### 9.1 当前能检查什么

- 世界与目录的指定版本是否匹配。
- 部分数值、时间、生死、关系反向记录、知识来源、物件引用、借款和任务关联是否满足领域规则。
- 事件与选项 ID 是否重复，事件触发类型是否支持，选项数量是否至少为二。
- 条件操作、效果操作、观察方向与证据强度是否位于当前白名单。
- 具体绑定下的选项是否能完成效果结算，既存任务是否仍可执行。

### 9.2 当前没有保证什么

- 完整 JSON 结构正确性与每个字段的静态类型；有些畸形输入仍可能产生普通 Python 错误，而不是统一的 `RuleError`。
- 目录中每个事件在全部可能世界中都可到达、可结束、不会形成叙事死循环。
- 自由文本与结构化事实逐句一致，NPC 动机符合现实常识，选项具有相当的吸引力。
- 所有模板条件路径、文本占位符和效果参数已在载入时完成静态验证；部分检查需要到具体场景执行时才发生。
- 内容去重、时代风格检查、专家审核、自动发布、质量评分或批量生成平台。
- 根据所有玩家的经历验证过的人格测量效度。

因此，当前输入应是可信作者审核过的内容。合理的人工流程是先读规则与实例，再审核模板与路径，在针对性的世界情境中试跑成功、失败、资源不足、死亡、延期等分支；不能把“通过载入检查”当成内容已全面合格。

### 9.3 未来字段应另行实现

下列字段可作为下一版设计方向，**当前引擎不解释它们，直接加入 JSON 不会生效**：

| 未来字段或机制 | 要解决的问题 |
|---|---|
| `cooldown` | 同类事件重复间隔 |
| `mutex` | 同一时期不可并存的事件或任务 |
| `dependencies` | 资产依赖与缺失内容检查 |
| `priority` / 叙事调度规则 | 合法事件间的紧迫性和节奏选择 |
| 通用多角色选择器 | 动态绑定家人、同事、组织与多名 NPC |
| `duration` 与日历占用 | 真实时间成本及日程冲突 |
| 提议、接受、拒绝与替代方案 | 通用 NPC 自主回应流程 |
| 通用到期义务 | 工资、房租、照顾安排和物品归还 |
| 内容审核与来源元数据 | AI 候选、人工审核、发布版本的管理 |
| 完整 JSON Schema 与静态路径检查 | 更早、更一致地拒绝结构错误 |

每扩展一个机制，都应同步更新操作解释、领域校验、样例内容和相应验证。世界规则支持的范围扩大以后，才适合批量生成依赖这些能力的新故事。
